# Apple-platform local Watch History persistence facts

Research for [Choose the local Watch History persistence and migration architecture](https://github.com/gridness/miraio/issues/20), 2026-08-21.

## Scope and evidence

This note compares SwiftData, Core Data with its SQLite persistent store, and app-owned SQLite for Miraio's profile-and-Episode Watch History contract. GRDB is included only as a representative maintained Swift wrapper; SQLite's own documentation remains the authority for database behavior.

- **Documented** means the linked owner documentation or source promises the capability.
- **Inference** means Miraio can build the required invariant from those capabilities, but the framework does not promise that invariant by name.

## Decision-grade comparison

| Concern | SwiftData | Core Data SQLite store | App-owned SQLite (optionally GRDB) |
| --- | --- | --- | --- |
| macOS 26+ and future iOS reuse | **Documented:** SwiftData is an Apple-platform framework, and `ModelConfiguration` supports an explicit store URL or app-group container. Its default store is backed by Core Data. ([SwiftData](https://developer.apple.com/documentation/swiftdata), [`ModelConfiguration`](https://developer.apple.com/documentation/swiftdata/modelconfiguration)) | **Documented:** Core Data and its SQLite store are available on macOS and iOS. The same managed-object model and persistence adapter can be kept outside platform UI code. ([`NSPersistentStore`](https://developer.apple.com/documentation/coredata/nspersistentstore), [`NSPersistentStoreDescription`](https://developer.apple.com/documentation/coredata/nspersistentstoredescription)) | **Documented:** SQLite is a portable C library. GRDB's current package manifest and README support both macOS and iOS and use the operating system SQLite by default. ([SQLite](https://sqlite.org/about.html), [GRDB README](https://github.com/groue/GRDB.swift), [GRDB `Package.swift`](https://github.com/groue/GRDB.swift/blob/master/Package.swift)) |
| Atomic checkpoint boundary | **Documented:** `ModelContext.transaction` runs a closure and then writes its pending inserts, changes, and deletes; `save()` writes pending changes. **Not documented:** SwiftData does not expose SQLite journal or `synchronous` durability settings as part of this API. ([`ModelContext`](https://developer.apple.com/documentation/swiftdata/modelcontext), [`transaction(block:)`](https://developer.apple.com/documentation/swiftdata/modelcontext/transaction(block:))) | **Documented:** a root context's `save()` attempts to commit its unsaved changes to the external store, and a persistent-store coordinator executes its work serially. SQLite-store configuration accepts SQLite pragmas, but Core Data owns the private store format. ([`save()`](https://developer.apple.com/documentation/coredata/nsmanagedobjectcontext/save()), [`NSPersistentStoreCoordinator`](https://developer.apple.com/documentation/coredata/nspersistentstorecoordinator), [persistent-store behavior](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreData/PersistentStoreFeatures.html)) | **Documented:** explicit `BEGIN`/`COMMIT` transactions are atomic; SQLite documents ACID behavior and the durability consequences of `PRAGMA synchronous`. A GRDB `DatabaseWriter.write` serializes writes and wraps the closure in a transaction. ([transactions](https://sqlite.org/lang_transaction.html), [atomic commit](https://sqlite.org/atomiccommit.html), [`PRAGMA synchronous`](https://sqlite.org/pragma.html#pragma_synchronous), [GRDB `DatabaseWriter`](https://github.com/groue/GRDB.swift/blob/master/GRDB/Core/DatabaseWriter.swift)) |
| Playback Session and monotonic sequence rejection | **Documented primitives:** compound uniqueness, predicates, serial model-actor isolation, and context transactions. **Inference:** a single store actor can fetch, compare the active Playback Session and sequence, mutate, and save as one operation. SwiftData exposes no documented conditional-upsert primitive that makes `incomingSequence > storedSequence` a store-level condition. ([SwiftData updates](https://developer.apple.com/documentation/updates/swiftdata), [concurrency support](https://developer.apple.com/documentation/swiftdata/concurrencysupport), [`ModelContext`](https://developer.apple.com/documentation/swiftdata/modelcontext)) | **Documented primitives:** compound uniqueness constraints, serialized context queues, optimistic-lock conflicts, and save merge policies. **Inference:** one private-queue store executor can implement the same compare-and-save rule, but multiple contexts require explicit conflict handling; Core Data exposes no supported SQL condition against its private store. ([uniqueness constraints](https://developer.apple.com/documentation/coredata/nsentitydescription/uniquenessconstraints), [`NSMergePolicy`](https://developer.apple.com/documentation/coredata/nsmergepolicy), [Core Data concurrency](https://developer.apple.com/documentation/coredata/nsmanagedobjectcontext)) | **Documented:** an UPSERT's trailing `WHERE` can turn `DO UPDATE` into a no-op based on old and incoming values. Together with a unique key and an explicit transaction, SQL can make session validity and increasing sequence a database-enforced conditional write and inspect affected-row count. ([UPSERT](https://sqlite.org/lang_upsert.html), [conflict clauses](https://sqlite.org/lang_conflict.html), [transactions](https://sqlite.org/lang_transaction.html)) |
| Composite indexes and deterministic keyset reads | **Documented:** `#Index` defines compound binary indexes; fetch descriptors accept predicates and ordered sort descriptors. **Limitation:** the public index macro does not specify sort direction or collation, and the backing SQL is not a public contract. ([SwiftData updates](https://developer.apple.com/documentation/updates/swiftdata), [`Index(_:)`](https://developer.apple.com/documentation/swiftdata/index(_:)-74ia2), [`FetchDescriptor`](https://developer.apple.com/documentation/swiftdata/fetchdescriptor)) | **Documented:** `NSFetchIndexDescription` contains ordered index elements, including an `ascending` setting, and fetch requests support multiple sort descriptors. Core Data's SQLite representation remains private and must not be queried or changed directly. ([`NSFetchIndexDescription`](https://developer.apple.com/documentation/coredata/nsfetchindexdescription), [`NSFetchIndexElementDescription`](https://developer.apple.com/documentation/coredata/nsfetchindexelementdescription), [persistent-store behavior](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreData/PersistentStoreFeatures.html)) | **Documented:** `CREATE INDEX` fixes the exact column order, direction, and collation; `ORDER BY` plus a row-value comparison implements keyset/scrolling-window pagination efficiently with a matching index. SQL and `EXPLAIN QUERY PLAN` are inspectable test surfaces. ([`CREATE INDEX`](https://sqlite.org/lang_createindex.html), [row values](https://sqlite.org/rowvalue.html), [query planner](https://sqlite.org/eqp.html)) |
| Explicit destructive deletes | **Documented:** delete one model, delete all models matching a predicate, or delete all container data; changes persist at the next save/transaction. ([SwiftData deletion](https://developer.apple.com/documentation/swiftdata/deleting-persistent-data-from-your-app), [`delete(model:where:includeSubclasses:)`](https://developer.apple.com/documentation/swiftdata/modelcontext/delete(model:where:includesubclasses:))) | **Documented:** normal context deletion participates in a save; `NSBatchDeleteRequest` deletes selected rows at the SQLite-store level but does not automatically merge those deletions into live contexts. ([`NSManagedObjectContext.delete`](https://developer.apple.com/documentation/coredata/nsmanagedobjectcontext/delete(_:)), [`NSBatchDeleteRequest`](https://developer.apple.com/documentation/coredata/nsbatchdeleterequest)) | **Documented:** `DELETE ... WHERE ...` selects exact rows and participates in the surrounding transaction. **Inference for every option:** invalidating Playback Sessions and deleting one entry or one profile must be one store operation so delayed observations cannot recreate data. ([`DELETE`](https://sqlite.org/lang_delete.html), [foreign keys](https://sqlite.org/foreignkeys.html)) |
| Versioned schema migration | **Documented:** ordered `VersionedSchema` definitions and `SchemaMigrationPlan` stages support lightweight and custom migrations. ([`SchemaMigrationPlan`](https://developer.apple.com/documentation/swiftdata/schemamigrationplan), [`MigrationStage`](https://developer.apple.com/documentation/swiftdata/migrationstage), [Apple's migration walkthrough](https://developer.apple.com/videos/play/wwdc2023/10195/)) | **Documented:** versioned models support inferred lightweight migration, staged lightweight/custom migration, and manual mapping-model migration. ([staged migrations](https://developer.apple.com/documentation/coredata/staged-migrations), [lightweight migration](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreDataVersioning/Articles/vmLightweightMigration.html), [manual migrations](https://developer.apple.com/documentation/coredata/manual-migrations)) | **Documented:** SQLite supplies transactional DDL and an app-owned `user_version`, but no application migration planner. GRDB's `DatabaseMigrator` records named migrations, applies unapplied migrations in registration order, and checks foreign keys before commit; its destructive schema-change option is explicitly for development, not release builds. ([`PRAGMA user_version`](https://sqlite.org/pragma.html#pragma_user_version), [`ALTER TABLE`](https://sqlite.org/lang_altertable.html), [GRDB `DatabaseMigrator`](https://github.com/groue/GRDB.swift/blob/master/GRDB/Migration/DatabaseMigrator.swift)) |
| Corruption detection and recovery | **Documented:** container creation, fetch, and saves throw, and the container can erase all data. **Not documented:** SwiftData exposes no store integrity-check or live-backup API. Its default store is opaque. ([`ModelContainer`](https://developer.apple.com/documentation/swiftdata/modelcontainer), [`SwiftDataError`](https://developer.apple.com/documentation/swiftdata/swiftdataerror)) | **Documented:** loading/saving can report store failures; coordinators can destroy a store or replace it from another store. Apple says the Core Data SQLite format is private and must not be inspected or manipulated with native SQLite. There is no public Core Data equivalent of `PRAGMA integrity_check`. ([`NSPersistentStoreCoordinator`](https://developer.apple.com/documentation/coredata/nspersistentstorecoordinator), [persistent-store behavior and security limits](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreData/PersistentStoreFeatures.html)) | **Documented:** `quick_check`, `integrity_check`, and `foreign_key_check` provide explicit detection. SQLite automatically recovers interrupted transactions when its journal/WAL remains paired with the database; the online backup API or `VACUUM INTO` makes a consistent copy of a live database. SQLite's optional recovery extension may salvage corrupt data but explicitly cannot promise perfect restoration. ([integrity pragmas](https://sqlite.org/pragma.html#pragma_integrity_check), [how corruption happens](https://sqlite.org/howtocorrupt.html), [backup API](https://sqlite.org/backup.html), [recovery extension](https://sqlite.org/recovery.html)) |
| Sandbox location, protection, and backup | **Documented:** all three can place their store under the sandbox container's Application Support URL; SwiftData can receive an explicit store URL. SwiftData's public configuration does not expose Core Data's file-protection option. | **Documented:** Core Data exposes `NSPersistentStoreFileProtectionKey`; Apple documents `Complete Until First User Authentication` as the iOS default for modern apps. | **Documented:** the app controls the database path and may apply Foundation file-protection attributes. **Inference:** it must treat the database and any journal/WAL sidecars as one storage unit and use SQLite's backup API rather than an uncoordinated file copy. |

The location and backup rules are technology-independent. Apple directs sandboxed apps to obtain their container location through `FileManager` and put managed support data in Application Support. On iOS, Application Support is backed up by default; `isExcludedFromBackup` is for cache or support data that is not needed in a backup. Apple documents per-file Data Protection classes on iOS and Apple silicon Mac, with a login/logout rather than lock/unlock boundary on macOS. ([App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [file-system placement and backup](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), [`isExcludedFromBackup`](https://developer.apple.com/documentation/foundation/urlresourcevalues/isexcludedfrombackup), [`FileProtectionType`](https://developer.apple.com/documentation/foundation/fileprotectiontype), [Apple platform Data Protection classes](https://support.apple.com/guide/security/data-protection-classes-secb010e978a/web), [`NSPersistentStoreFileProtectionKey`](https://developer.apple.com/documentation/coredata/nspersistentstorefileprotectionkey))

**Inference for Miraio:** canonical Watch History is not a recreatable cache, so backup exclusion would trade away restoration after device replacement. Whichever persistence technology is selected should make that policy explicit and test the main file plus all sidecars on macOS and future iOS.

## Current SQLite runtime gate

**Documented:** SQLite's WAL documentation identifies a rare WAL-reset corruption bug in versions 3.7.0 through 3.51.2 when multiple connections write or checkpoint concurrently; fixes begin at 3.51.3 and named backports. Xcode 26.6's macOS 26.5 SDK header and the installed runtime report SQLite 3.51.0. GRDB's `DatabasePool` uses WAL and multiple connections, while `DatabaseQueue` is single-connection. ([SQLite WAL-reset notice](https://www.sqlite.org/wal.html#the_wal_reset_bug), [GRDB database connections](https://github.com/groue/GRDB.swift#database-connections))

**Inference for Miraio:** any multi-connection WAL design must verify the actual runtime SQLite version and fix status on every supported OS, or bundle a fixed maintained SQLite variant. A single serialized connection or non-WAL mode avoids that particular precondition and should be measured against the app's small-write/read responsiveness needs. This is a release gate, not a reason to weaken the store abstraction.

## Implications to take into the decision

- All three approaches can support the contract if Watch History mutations are isolated behind one UI-independent store executor shared by macOS and future iOS code.
- SwiftData documents compound constraints/indexes, transactional saves, explicit deletes, and versioned migrations, but its public surface leaves physical index details, conditional stale-write rejection, integrity checking, durability tuning, and file-protection configuration comparatively opaque.
- Core Data exposes more store controls than SwiftData—ordered fetch indexes, conflict policies, file protection, store replacement, and mature migration paths—while still forbidding direct inspection of its private SQLite representation.
- App-owned SQLite exposes the strongest documented primitives for a store-enforced monotonic update, exact keyset index, durability policy, integrity checks, and consistent backup. That control also makes Miraio responsible for SQL schema design, migration/recovery policy, and either a C adapter or a pinned third-party wrapper.
- GRDB reduces Swift integration and migration/concurrency plumbing, but does not change the SQLite guarantees or remove third-party dependency ownership. Its wrapper behavior should be pinned to a reviewed release and tested; the product decision should not rely on README feature labels alone.

These implications distinguish the tradeoff; they do not select the persistence architecture.
